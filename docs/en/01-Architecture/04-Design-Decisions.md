# 🧭 Design Decisions

## Intentional decisions

| Decision | Rationale |
|---|---|
| **Event-driven with Kafka** between order → payment → notification | Decouples services; the producer doesn't wait on the consumer |
| **A shared `shared-lib`** (constants, event DTOs, `JwtUtil`, exceptions) | Avoids duplicating event contracts and JWT utilities across modules |
| **MapStruct** for entity ↔ DTO/event mapping | Reduces manual conversion boilerplate |
| **Resilience4j** (`Retry` + `CircuitBreaker`) around the Stripe call | Stripe is an external dependency; protects the flow against transient failures |
| **`GlobalExceptionHandler`** (`@RestControllerAdvice`) per service | Consistent error responses within each service |
| **"Soft" sale cancellation** (`DELETE` → `status=CANCELLED`) | Preserves history; disallows cancelling once `PAID` |
| **Secrets via `.env`** (gitignored) + `bootRun` injects them as environment variables | Avoids committing the JWT secret, the Stripe key and the MySQL password; see [[../02-Setup/02-Local-Setup|Local Setup Guide]] |
| **Shared JWT** across `api-gateway`, `order-service` and `payment-service` (same `app.jwt.secret`) | `api-gateway` signs, the other two validate — same HS256 symmetric key |
| **`GenericResponse` via inheritance** (not a `data` wrapper) to homologate responses | Each concrete response (`LoginResponse`, `CarSaleResponse`, `PaymentResponse`...) extends `GenericResponse` and adds `response_code`/`description`/`timestamp`, keeping its business fields "flat"; see [[../04-API-Reference/00-Response-Format\|Response Format]] |
| **Public Swagger UI** (no JWT needed to open it) on all 3 REST services | Prioritizes demo/portfolio use: anyone can explore the API with zero friction; the "Authorize" button (JWT) still protects the actual calls into `order-service`/`payment-service` |

See also the full pattern breakdown in [[../06-Technologies/02-Patterns-Used|Patterns Used]].

## ✅ Resolved

> [!tip] These were the two limitations flagged as most critical; they're now fixed and verified live (register → login → authenticated call into `order-service`/`payment-service`).

- **🔐 Security on internal services (resolved).** `order-service` and `payment-service` now have Spring Security + their own `JwtAuthenticationFilter` (same pattern as `api-gateway`), and require a valid JWT on **every** endpoint (`anyRequest().authenticated()`). A request with no token, or an invalid/expired one, gets **`401 Unauthorized`** with a homologated `GenericResponse` body (thanks to a per-service `RestAuthenticationEntryPoint`) — before this change it was a bare `403 Forbidden` with no body. See [[../03-Services/02-Order-Service|Order Service]] and [[../03-Services/03-Payment-Service|Payment Service]].
  - `notification-service` was left **unchanged on purpose**: it exposes no REST endpoint (it's a pure Kafka consumer), so there's nothing for Spring Security to protect there.
- **🔑 Plaintext secrets (resolved).** `app.jwt.secret`, `stripe.api.key` and the MySQL password (`spring.datasource.password`) are no longer hardcoded: `application.properties` now reference `${JWT_SECRET}` / `${STRIPE_API_KEY}` / `${DB_PASSWORD}`, and those values live in a root-level `.env` (added to `.gitignore`). Each `build.gradle` (all 4 services) has a `bootRun { doFirst { ... } }` block that reads that `.env` and injects it as process environment variables, so `./gradlew :service:bootRun` still works with no manual steps. `docker-compose.yml` also references `${DB_PASSWORD}` for `MYSQL_ROOT_PASSWORD`/`MYSQL_PASSWORD` (Docker Compose reads the same `.env` automatically). A `.env.example` (no real secrets) was added as a template.
- **📐 Homologated response format (resolved/added).** `GenericResponse` (`shared-lib`) replaces the old `ApiErrorResponse` (which only covered errors). Now **every** response — success or error, including the 401s generated by Spring Security — follows the same `response_code`/`description`/`timestamp` shape. See [[../04-API-Reference/00-Response-Format|Response Format]].
  - This does **not** fix the casing inconsistency across services (`order-service` still uses `snake_case`, `payment-service` still uses `camelCase` for its business fields) — see [[../07-Testing/01-Postman-Collection|Postman Collection]]. It only homologates the "envelope" (`response_code`/`description`/`timestamp`), not each payload's internal fields.
  - **Explicitly confirmed decision:** items inside a list (e.g. `sales` in `GET /sales/customer/{id}`) do NOT carry their own `response_code`/`description`/`timestamp` — only the wrapper (`CarSaleListResponse`) does. Forcing `"00"` onto every item was considered and dropped, since it would just repeat the same value with no new information (an item can never fail independently in this code: if something goes wrong, the whole query breaks). Full explanation in [[../04-API-Reference/00-Response-Format|Response Format]].
- **✅ Input validation (added).** `RegisterRequest`, `LoginRequest` and `CreateCarSaleRequest` now use Bean Validation (`@NotBlank`, `@Email`, `@Size`, `@Positive`, etc.) via `@Valid`; path variables (`saleId`, `customerId`) are validated with `@Positive` via `@Validated`. Failures are homologated as `response_code: E005`, combining every failing field into a single message. Verified live: invalid email, short password, wrong-length VIN, negative year/mileage/price, and negative-or-zero IDs — all rejected before ever reaching the controller. See [[../04-API-Reference/00-Response-Format|Response Format]].
  - Technical note: in `api-gateway`, `GlobalExceptionHandler` extends `ResponseEntityExceptionHandler` (for general Spring MVC exception handling), which already intercepts `MethodArgumentNotValidException` internally — adding another `@ExceptionHandler` for that same type caused a startup failure ("Ambiguous @ExceptionHandler"). The correct fix is overriding the protected `handleMethodArgumentNotValid(...)` hook instead of declaring a new handler.

## 🚧 Known Limitations (Technical Debt)

> [!warning] These observations come from a direct review of the source code. They're useful for knowing what NOT to carry forward if this project moves toward production.

- **🏷️ The "API Gateway" isn't a gateway.** It doesn't route or proxy traffic — it's only an authentication service. A client must know and call each microservice's URL directly.
- **💳 The payment always "succeeds".** `PaymentServiceImpl` sets the status to `PAID` right after creating the Stripe `PaymentIntent`, without checking the actual returned status (`requires_action`, `processing`, etc.). The code itself documents this as a test-mode simulation.
- **✉️ Simulated notifications.** There is no real integration with any email or SMS provider; `notification-service` only writes formatted "email"/"SMS" log lines.
- **📉 No Dead Letter Topic or Kafka retries.** Exceptions thrown inside the `@KafkaListener` methods of `payment-service` and `notification-service` are only logged — the message is neither requeued nor moved to an error topic.
- **🧬 Version drift across modules.** The root `build.gradle` pins Spring Boot `4.0.8-SNAPSHOT`, but `order-service` and `payment-service` declare `4.1.0` in their own `build.gradle` files. Similarly, `shared-lib` declares `auth0:java-jwt:4.6.0` and `jackson-databind:2.22.1`, while the root manages `4.4.0` and `2.17.0` respectively. Centralizing versions in a single BOM/catalog is recommended.
- **🗃️ Shared database across services.** All four services connect to the same `order_platform` schema instead of having independent databases — a practice that contradicts the typical "database per service" microservices principle.
- **⚙️ Unused property.** `stripe.api.version=2023-10-16` is defined in payment-service, but no code reads it; the effective API version is whatever the `stripe-java:23.10.0` SDK defaults to.
- **👤 Unused MySQL user.** `docker-compose.yml` creates a `user`/`password` account, but every service connects as `root`.
- **🎭 No role-based access control (RBAC).** The `User.role` field is always saved as `"USER"` (never `"ADMIN"`), and all three `JwtAuthenticationFilter` copies (gateway, order, payment) build the authentication with an empty authorities list — there is no `@PreAuthorize`/`hasRole` anywhere in the codebase. Current security only distinguishes "authenticated" vs "not", not roles.
- **🔁 A nuance in the payment retry flow.** The "does a Payment already exist?" check in `PaymentServiceImpl.processPayment` doesn't distinguish the existing record's status — it also matches the `PENDING` row that `handlePaymentFailure` creates after the first failure. With the current logic, a reprocessed event won't retry against Stripe in that scenario, so the path toward `FAILED` (after 3 failures) would need that check to distinguish an already-resolved payment from one still pending. Confirmed with `PaymentServiceImplTest`. See [[../03-Services/03-Payment-Service|Payment Service]].
